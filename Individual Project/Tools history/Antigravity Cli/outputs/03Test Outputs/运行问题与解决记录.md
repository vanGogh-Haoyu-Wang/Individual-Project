## 3. 遇到的问题、根因和解决方法

### 问题 1：`julia` 启动器无法创建锁文件

**现象**

直接运行 PATH 中的 `/Users/vangogh/.juliaup/bin/julia` 时失败：

```text
The Julia launcher failed to load a configuration file.
Could not create lockfile /Users/vangogh/.julia/juliaup/.juliaup-lock:
Operation not permitted (os error 1)
```

**根因**

沙箱允许读取用户 Julia 安装，但不允许启动器在 `~/.julia/juliaup` 写锁文件。

**解决**

绕过 juliaup 启动器，直接使用真实 Julia 1.12.6 二进制：

```text
/Users/vangogh/.julia/juliaup/julia-1.12.6+0.aarch64.apple.darwin14/Julia-1.12.app/Contents/Resources/julia/bin/julia
```

同时把可写的本地 depot 放在 `JULIA_DEPOT_PATH` 第一项，把现有 `~/.julia` 放在第二项供只读加载包源码。这样预编译缓存写入输出目录，不触碰受限位置。

### 问题 2：通用工作簿导入器耗尽约 4 GB Node 堆

**现象**

用工作区的通用电子表格导入器检查这份约 1.7 MB 的文件时，进程约 66 秒后退出，退出码 `134`：

```text
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
```

**根因**

该路径会展开完整工作簿对象，内存占用远大于文件体积；这不是生成五张图所必需的读取方式。

**解决**

改用任务要求的 `XLSX.jl` 定向读取工作表名、尺寸和 `CT07` 的必要单元格。检查约两秒完成，结果记录在 `workbook-inspection.txt`。

### 问题 3：原脚本退出码为 0，但输出 0 张图片

**现象**

把 Excel 绝对路径作为命令行参数运行原脚本，退出码为 `0`，stdout/stderr 都为空，输出目录中 PNG 数量为 `0`。完整证据见 `01-original-run.log`。

**根因**

原脚本末行真正调用主函数的语句被注释：

```julia
# figs = process_acoustic_emission_data()
```

此外，原脚本没有读取 `ARGS`，所以传入的数据库绝对路径实际上没有被使用。

**解决**

修正版增加命令行入口，明确接收 Excel 绝对路径和输出目录，并实际调用 `process_acoustic_emission_data(...)`。

### 问题 4：默认工作表名错误

**现象**

手动调用原函数并使用其默认表名 `CT-07` 时，稳定复现：

```text
ERROR: XLSXError: `CT-07` is not a valid SheetCellRef.
```

错误指向原脚本第 23 行。

**根因**

工作簿实际表名是 `CT07`，没有连字符。

**解决**

修正版默认使用 `CT07`，并在读取前检查表名；若不存在，会列出实际可用表名。

### 问题 5：整列 `Float64.(...)` 转换遇到标题和空值

**现象**

把表名改为 `CT07` 后，原函数继续在第 35 行失败：

```text
ERROR: MethodError: no method matching Float64(::Missing)
```

**根因**

工作表前三行混合标题、单位、数值和空值，八个目标列在 DataFrame 中全部成为 `Any`。机械数据从第 4 行开始，而 AE 数值从第 2 行已经开始，两套系统不能用同一个简单起始行粗暴裁剪。

**解决**

保留原来的 1-based 列映射，但分别建立两组“所有所需列均为有限实数”的行掩码：

- 机械组：列 `1, 3, 4`，用于 `t1, strain, stress`；
- AE 组：列 `5, 9, 10, 12, 14`，用于 `time, rms, cumrms, energy, cumenergy`。

筛选后再广播转换为 `Float64`，既去除标题/空值，也保持每组通道内部对齐。

### 问题 6：`display(fig)` 不等于保存图片

**现象**

原函数即使能执行，也只调用 `display(fig1)` 至 `display(fig5)`，没有文件输出语句。

**根因**

`display` 面向交互式显示；在无 GUI 的批处理环境中不会自动生成 PNG 文件。

**解决**

修正版对五个图对象逐一调用 `savefig`，并使用固定、可审计的文件名。设置 `GKSwstype=100` 让 GR 在无窗口环境中稳定渲染。

### 问题 7：首次预编译出现受限端口警告

**现象**

第一次加载依赖时，Julia 进行了约三分钟的预编译。HTTP.jl 的预编译 workload 尝试绑定本地端口，沙箱返回 `EPERM`，但包管理器明确将其记录为“忽略的预编译 workload 错误”，最终 Plots 及全部依赖预编译成功，原脚本退出码仍为 `0`。

**根因**

HTTP.jl 的测试型预编译 workload 涉及本地监听套接字；当前任务本身不需要网络服务。

**解决**

无需修改科学计算代码。继续使用本地可写 depot；后续运行直接复用缓存，最终绘图约 11 秒完成，stderr 为空。

### 问题 8：首次视觉检查发现双轴标签被画布裁切

**现象**

第一轮五图在数量、PNG 格式与尺寸测试中通过，但逐图查看发现左/右纵轴标题贴边，尤其 `twinx()` 的右轴标题有裁切。

**根因**

默认边距没有为叠加的右纵轴标题预留空间。

**解决**

只增加左边距 `10 mm` 和右边距 `18 mm`，不改变数据、标题、轴范围或绘图类型。重新生成后，五张图的左右轴标题均完整可读。
